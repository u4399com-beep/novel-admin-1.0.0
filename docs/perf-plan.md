# 章节采集提速方案（R106 规划）

> 状态：P0-1/P0-2/P1-2 已实施（2026-10-09，R107）；P1-1/P1-3 经实施期复评暂缓（理由见各项标注）。
> 基于 worker.go / runner.go / scraper-go ratelimit.go / chain.go 实码调研 + 在库任务实测速率，
> 非拍脑袋估算。实施按 P0→P1→P2 分期，每期独立可验证、可回滚（各自 env 开关）。

## 一、现状与瓶颈量化（全部实测）

### 1.1 速率基线

| 任务 | 站点形态 | 实测均速 | 备注 |
|---|---|---|---|
| #8 | 常规站 | **756 章/h** | 首尾跨度含 paused 窗口，偏保守 |
| #11 | 常规站 | 588 章/h | 同上 |
| #10 | 常规站 | 351 章/h | 同上 |
| #16 | 严格限流站 | 35 章/h | biqutu（407/黑洞站形态） |
| #15 | 直连失败站 | 20 章/h | minyuan |
| R104 #1 | browser 策略站 | ≈1500 章/h（2.4s/章） | 101kks 挑战页，browser 1-5s/章 |

**理论天花板**：单域合规间隔 1200ms（±抖动）→ curl 快通道理想 ≈ **2400 章/h**；
browser 策略站（网络时间 2-5s）≈ **1200 章/h**。实测只跑到理论值的 15-50%。

### 1.2 耗时构成拆解（单章）

```
单章墙钟 = max(域槽礼貌间隔, 网络服务时间) + 落库 + 队列调度
           ├─ 域槽间隔: 1200ms 基线（scraper-go ratelimit.go:6 合规红线 <1000ms 禁止）
           │   ├─ AIMD 退避位: 限流时 ×1.5 至上界 8s；每成功 -50ms 回落
           │   └─ politenessExtra: 连续 200 请求 +100ms，上界 300ms
           ├─ 网络时间: HTTP/curl 策略 0.3-1s；browser 策略 1-5s（渲染）
           ├─ 策略预算: 20s/策略（车道排队 18-30s → timeout-budget 全灭）
           └─ 落库: R103 已单章双写单事务，~5-15ms（非瓶颈）
```

### 1.3 已就位的机制（不重复建设）

- affinity 策略提位（最快策略自动升链首）
- 车道 AIMD 双层自适应（软起步 4 → 上限 12；限流降档 12→4→2；连捷 24 章回开；EWMA 排队冻结防 boom-bust）
- 任务级并行（runner 每轮领 5 pending，goroutine 无总量上限；fleet-keeper 14+ 规则各自建任务=多域天然并行）
- HTTP keep-alive（MaxIdleConns=64）+ gzip/deflate 透明解压
- 连败熔断/自动恢复（防烧穿 + paused 自愈）
- R103 章节正文+字数双写单事务

### 1.4 瓶颈结论

1. **单域吞吐被礼貌间隔+网络时间双重钳制**：加车道无收益（纯过订阅，EWMA 冻结已实证）；
   网络时间 > 间隔时（browser 站），网络是实际瓶颈。
2. **书间串行是结构浪费但只在多域任务里有收益**：fleet 每任务=单站多书（同 host），
   书间并行不增加单域吞吐；只有聚合多域任务才受益。
3. **Phase1 全部完成才开始 Phase2**：目录采集（Phase1）期间填充车道完全空闲；
   Phase1→2 之间还有 3s 礼貌休整。
4. **舰队大面积 paused**（14 条）：代理不可用/失败保护，多域并行度远低于规则数。
5. 落库/进度 flush 已优化到位，**不再是**瓶颈。

## 二、分期实施方案

### P0（低风险高收益，先行）

**P0-1 快通道策略探测收紧**（scraper-go chain.go / affinity.go）
- 现状：全链按序尝试，affinity 事后提位；browser 站每章仍可能多付一次探测。
- 改造：首章探测成功后锁定策略链（picking 预算从「每章尝试」改「会话级锁定」+ TTL 复探）；
  对 HTTP 200 且正文完整的站点直接固定 curl/http 策略，跳过 browser 提位窗口。
- 预期：browser 混合站单域 750 → 1200-1500 章/h（网络时间 2.5s→0.3s 后 max(1.2s, 网络) 由网络侧转为间隔侧）。
- 风险：低——锁定仅在同域连续成功时保持，遇挑战/空壳立即解锁回退全链（现有 soft-block 判定复用）。
- **【已实施 R107】**：scraper-go 新增 sessionlock.go（慢锁标记/清除/周期复探/预算闸 8s）+ chain.go
  接线（Tier 1/2 成功清锁、Tier 3 成功标记慢锁；每 30 次链尝试或锁龄超 2 分钟把首个可用
  Tier 1 策略插到链首复探）+ /api/strategies.slowLock 观测。开关 PROBE_SLOW_LOCK_OFF=1。
  生产实证：101kks.com 慢锁命中后复探按期触发（任务日志 [fast-probe] 行），未命中时本轮
  照旧由 browser 出正文（失败章节零新增）；快站全部处于 HTTP 快通道无需复探。

**P0-2 唤醒 paused 舰队**（运维 + api 侧联动）
- 现状：14 条 paused（代理 407/黑洞/直连失败）；代理池 448 个存活但部分规则未路由到可用出口。
- 改造：①proxypool 连通性体检任务（已有收割循环）对 paused 规则逐条重测出口；
  ②autoResumePausedTasks 已每 30s 扫限流类；补「代理恢复即 resume」事件联动。
- 预期：多域并行度 5→12+，**总吞吐直接 ×2 以上**（域间天然并行，零代码风险）。
- 风险：低——自动恢复已有每任务 4 次上限防抖。
- **【已实施 R107】**：runner.go 新增 ①启动孤儿唤醒 resumeRestartOrphans（「服务重启，任务自动暂停」
  前缀专属匹配→pending，恢复后文案改写防崩溃循环风暴）②封禁形态有界自动恢复
  autoResumeBlockedTasks（静默 ≥30min + 代理池存活 ≥3 + 每任务 ≤2 次 + 每轮 ≤2 条）。
  生产实证：重启暂停 11 条→自动归队 11 条（14:37:51 同秒），fleet 并行度 5→13 running；
  词表契约测试 runner_resume_blocked_test.go（含幂等/上限/静默期/代理池前置四场景）。

### P1（结构性改造，中等风险）

**P1-1 Phase1/Phase2 流水线重叠**（worker.go runList）
- 现状：Phase1 全部书目录入库完 → 3s 休整 → Phase2 按 novelId 升序逐本填。
- 改造：书级完成即投入 fill 队列（书间仍串行，但 Phase1 剩余书目录采集与已完成书的
  章节填充**并行**——两者读写不同表、域槽同 host 共享队列天然互济）。
- 预期：端到端时延 -30~50%（大 list 任务 Phase1 占比 10-30%）。
- 风险：中——Phase2 熔断需能反压 Phase1（stopState 检查点已贯穿两阶段，复用）；
  fillMap 构建需改流式（骨架 upsert 返回 novelId 后即可 enqueue）。
- **【R107 实施期复评：暂缓】**：单域任务 Phase1/2 共享同 1.2s 域槽——重叠不增吞吐
  （总请求数×间隔不变），仅省 3s breather；跨域收益已被 P1-2 书间并行覆盖（Phase1 本身
  经 BOOK_CONCURRENCY=4 天然跨域并行）。流式 fillMap 重构风险/收益比不划算，待出现
  「Phase1 占比 >30% 的多域大列表」实证再启用。

**P1-2 聚合任务书间并行池（host 感知）**（worker.go phase2Fill）
- 现状：`for _, novelID := range ids` 严格串行。
- 改造：按 host 分组的书间并行池（默认 2-3 书并发）；**同 host 书不并行**（域槽排队无收益），
  跨 host 并行使多域任务吃到多域槽。聚合源（多站点规则）收益显著；单站任务自动退化为串行（无副作用）。
- 预期：多域任务吞吐 ×2-3；单站任务 0%（诚实标注）。
- 风险：中——laneCtl/统计计数器需按书隔离（atomic 已是共享安全）；fillMap 只读无竞态。
- **【已实施 R107】**：worker.go phase2Fill 重构——fillMap 构建期快照 plans（workers 只读）、
  delete 经 mapMu 串行化、breakerStopped 原子化；按 plan.Referer（兜底首章 URL）host 分组，
  组间并行（默认 ×2，SCRAPE_BOOK_PARALLEL 可调）组内严格串行；熔断后 workers 持续 drain
  至 close（生产端不死锁）。回归：worker_bookparallel_test.go 三测（多域并行/单域退化串行/
  熔断 drain 30s 看门狗）+ -race 通过；单站 fleet 任务自动退化串行零行为变化。

**P1-3 落库微批**（worker.go persistChapterFill / db.go）
- 现状：单章单事务（R103）。
- 改造：同书相邻章攒 8-16 章批量事务（批内任一失败回退单章路径）；确认 WAL `synchronous=NORMAL`。
- 预期：<1%（礼貌间隔 1.2s 面前落库 5-15ms 可忽略）——**低优先级，顺手做**。
- 风险：低。
- **【R107 实施期复评：不做】**：12 车道并发下「同书相邻章攒批」需跨车道汇合协调，
  复杂度与 R103 单章事务原子性保证冲突；实测落库 5-15ms 对 1.2s 间隔 <1%，且
  WAL+synchronous=NORMAL 已确认就位（db.go DSN）。投入产出不成正比，关闭此项。

### P2（激进项，默认关闭，需明确接受风险再开）

**P2-1 代理多 IP 分桶**（scraper-go ratelimit.go）
- 现状：域槽 per-host 全局 1.2s——多代理同 host 也共享一个间隔。
- 改造：hostSlot 键从 `host` 扩为 `host|proxyExit`，每桶独立 1.2s（每 IP 各自合规）。
- 预期：单域吞吐 ×N（N=可用出口数），对封 IP 型站点（trxsw/biqutu 实证）收益最大。
- 风险：**高**——源站总 QPS 上升 N 倍，违反「对单站礼貌」原则，可能触发全站封禁/临检。
  仅对已证实「按 IP 限流」的站点开启（规则级开关），默认 off。

**P2-2 CloakBrowser 实例池**（scraper-go browser.go / cloak）
- 现状：fetch-cloak 在沙箱 unavailable；服务器部署后挑战页站（101kks 形态）走 browser 1-5s/章。
- 改造：CloakBrowser 常驻实例池（2-4 实例复用，省每次冷启动），配合 P0-1 会话锁定。
- 预期：挑战站 1500 → 2000+ 章/h。
- 风险：中——内存/句柄常驻，需池化泄漏保护。

## 三、验收口径

- 单域速率：P0 后常规站 ≥1500 章/h（现 350-756）；挑战站 ≥1500 章/h。
- 舰队并行：running 任务数 ≥10（现 5）；全库日增量 ≥5 万章（现约 1.5-3 万）。
- 稳定性：熔断率不升（PHASE2_FAIL_BREAKER 触发次数/日不增）；429 占比不升。
- 每期独立开关（env），可随时回退旧行为。

### P3-1 失败章轮内回收重试轮（本轮实施）

- 现状：phase2 单轮内失败章（200 空壳/挑战窗口/限流窗口/预算耗尽）只留骨架，
  恢复要等 fleet 下一轮：45min 冷却 + 重扫列表页 + 重抓书页目录 diff——瞬态失败
  的回收延迟以**小时**计，且恢复路径本身消耗大量域槽预算。
- 改造（worker.go phase2Fill）：主循环把失败章记入回收队列（novelID+行+URL+referer）；
  全部书处理完且未熔断/未停止时，冷却 30s 后开始回收重试轮（默认 2 轮，轮间再冷却；
  每轮上限 2000 章）。重试轮完整复用主路径语义：laneCtl 车道闸/限流降档/连败熔断/
  EWMA 饱和感知/persistChapterFill 持久化——重试轮内再失败留骨架（下轮 fleet 兜底）。
- env：`SCRAPE_RETRY_PASSES`（默认 2，0=关）、`SCRAPE_RETRY_MAX_ROWS`（默认 2000）。
- 预期：挑战站/限流站的**轮内失败回收率即采即得**——实证失败形态统计中「限流/空壳」
  占大头的站点，单任务交付章数 +10-30%；省掉失败章的跨轮恢复开销（45min 级 → 30s 级）。
- 风险：低——有界轮数+章数上限+熔断/停止全检查点；重试失败不惩罚（骨架保留）。

### P3-4 fleet 增量快进（本轮实施，关关「连载监听」保守版）

- 现状：fleet 刷新任务对**已采完的书**仍逐本重抓书页+目录页（upsertBook 按
  title+author 去重发生在书页抓取**之后**）。成熟库每轮刷新白烧 200-400 书页请求
  ≈ 5-15min 域槽时间——这正是 R104 观察到的「aijjxs 目录分离形态长窗口」浪费源。
- 改造：①Novel 加 `tocScannedAt` 列（目录最近扫描时刻，ms）；②phase1Skeletons
  抓书页**前**快进判定：列表条目（title+author 双键，与 upsertBook 同键）命中
  「库内已有 + 空骨架清零 + tocScannedAt 在窗口内」→ 跳过书页/目录重抓，视作一次
  扫描（tocScannedAt 续期）；③真实扫描成功后同样续期。
- 三重条件缺一不可的安全设计：书不在库 → 必须抓（新书发现不受影响）；有空骨架
  （wordCount=0）→ 续传 FillRows 的 URL 依赖目录 diff，必须抓（失败章续传不受影响）；
  窗口外 → 连载可能有新章，必须抓（**连载更新零损失**——只省「确认没更新」的重复请求）。
- 双键保守规则：条目 author 为空时不快进（title 单键撞名风险不做）——列表页无作者
  的规则自动退化为原行为（零风险）。
- env：`SCRAPE_TOC_REFRESH_HOURS`（默认 6，0=关）。
- 预期：成熟库 fleet 刷新任务 Phase1 请求量 -70-90%；刷新任务更快进入有效填充阶段；
  同 host 的域槽预算更多让给正文填充与新增书目。
- 风险：低——保守判定 + 三重条件 + env 开关；最坏情形=多抓（退化为原行为）。

### P3-2 规则级镜像域名轮换（设计成稿，待镜像验证工具后实施）

- 关关「多书源」本质：同一内容多个入口 → 入口级独立限速域 → 吞吐 ×N。
- 改造设计：ScrapeRule 加 `mirrorHosts`（逗号分隔）；引擎 fetchPage 前按健康度/轮转
  把 URL 的 host 替换为镜像域（路径结构一致性由规则作者保证）；镜像域各自独立域槽
  （host 键天然隔离）→ 单规则多域并行；镜像连败自动回主域并降权（复用 hosthealth）。
- 前置条件：镜像连通性+内容一致性抽样比对工具（首章正文双域 hash 对比），防止
  路径结构不同的假镜像烧穿。默认关（规则级开关）。
- 预期：有镜像的站点单规则 ×N（N=可用镜像数）；无镜像站零变化。

### P3-5 同域任务单飞行（复评：不做）

- fleet-keeper 已有同规则活跃任务去重（pending/running/paused 任一存在即跳过）；
  两规则同 host 属罕见配置。现有共享域槽已保证同 host 合规速率，收益不成立。

### P3-3/P3-6（沿用 P2-1/P2-2）

- 代理 per-IP 域槽分桶（P2-1）：实施期复评补充设计——引擎已有 per-request 代理轮换
  （proxyCursor）与出口独立熔断（E17），分桶只需把 `acquireDomainSlot(host)` 的键扩为
  `host|egress`（pickProxy 先行）。维持默认关（对单站总 QPS ×N 的礼貌性风险）。
- CloakBrowser 实例池（P2-2）：维持（依赖服务器部署）。

# 章节名序号排序探讨（R106 第二项）

## 结论先行：**可行，且系统已实现 80%——剩余是三个缺口**

### 现状盘点（全部实码验证）

| 能力 | 状态 | 位置 |
|---|---|---|
| 序号解析器 | ✅ 完备 | chapterorder.go `parseChapterNo`：`第N章/节/回/话`（阿拉伯 1-7 位/全角/中文数字 1-12 位）、`123.`/`123、`/`123:` 前缀、`【第1章】`装饰前缀 |
| 中文数字 | ✅ | `chineseNumeralToInt`：零〇一二两三四五六七八九十百千万（两百零三/三千五百万） |
| 采集时自动重排 | ✅ 已接线 | worker.go:557 Task 48——Phase1 骨架入库前 `reorderRefPairs`，阈值 DISORDER_RATIO=0.2 |
| 存量审计+重排 API | ✅ | `GET/POST /api/novels/resort-chapters`（R101 卷感知 Vols 版，两阶段改号防唯一冲突） |
| 未编号章处理 | ✅ | 番外/序章锚定前一编号章之后，不丢章 |
| 乱序实测 | — | 当前库 975 本中 **17+ 本**为乱序候选（disorder 0.22~1.0，如《人在欧洲》302 章全乱） |

### 三个缺口（建议补齐项）

1. **存量候选无人触发**：17 本候选躺在审计结果里，POST 端点需手动调用且全库有
   pending/running 任务时 409 拒绝。建议：admin UI 加「全站目录体检」按钮（一键审计→逐本重排），
   或 fleet 空闲窗口自动执行。
2. **采集路径未用卷感知版**：worker.go:557 走旧版 `reorderChapterRefs`（无分卷分段），
   R101 只升级了 API 路径（`reorderChapterRefsVols`）。分卷书（候选中 1 本 volumeSegments=1）
   卷内乱序+卷间完整的形态会被误判。建议：采集路径统一换 Vols 版（refs 带空卷信息时行为与旧版一致，零破坏）。
3. **任务收尾无自动体检**：finalize 只回填简介/字数，不做单书乱序检测。
   建议：finalize 对涉及书跑 `resortDetectOrder`（只读、毫秒级），超阈值书自动重排——
   有 DISORDER_RATIO=0.2 阈值 + ≥8 章下限双保险，不会误伤已有序目录。

### 为什么「直接按序号排 idx」不作为默认行为

- 源站目录顺序通常是权威的（作者编排），乱序多源于**源站页面结构**（最新章节块混入/分页拼接错位）；
- 序号解析有 miss 形态（「上篇」「（5）」无「第…章」壳），全量按序号重排会让 miss 章节聚堆；
- 现行「阈值触发才重排 + 未编号锚定 + 稳定排序保留同号相对序」是更安全的折中——
  已有序目录 0% 乱序不动，真乱序（>20%）才修正。

### R110 新增机制（性能相关部分）
1. **cloak cookie 回存**（最大杠杆）：cloak 过盾后 context cookies（cf_clearance/PHPSESSID 等）
   回传引擎 jar（server.py /cloak 响应 + strategy_sidecar 回存）。挑战站从「每章重打挑战
   10-17s」变为「一次攻克 + 快通道亚秒/章」——与 P0-1 慢锁复探形成闭环：复探命中即亲和
   接管快通道，cookie 过期后 browser/cloak 自动重新攻克再 bank。
2. **GoEdge 概率挑战原地重掷**：fetch-curl 识别 307→/WAF/VERIFY/* 不跟随、重试同 URL
   （WAF_VERIFY_RETRY 默认 3）。非验证码破解（不与挑战交互），仅利用 WAF 自身的随机放行。
3. **进程组击杀**（稳定性→间接吞吐）：browser 桥接超时全树 SIGKILL，杜绝 Chromium 孤儿
   吃满线程配额导致的 pthread_create EAGAIN 连锁全灭（R110 实测根因）。
4. **stealth 单实例锁 + driver janitor + 池 4→2**：侧车自身的资源上界（线程配额 ~925 的
   环境里 4 cloak 实例 + rebuild 漂移足以打穿）。
